# Architecture

## Stack and why

| Layer         | Choice                          | Why                                                                                                                      |
| ------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Build         | Vite 8 + `@vitejs/plugin-react` | Fast dev server, zero-config production builds, first-class Vitest integration                                           |
| Language      | TypeScript (strictest flags)    | `strict`, `noUncheckedIndexedAccess`, `noImplicitOverride`, `verbatimModuleSyntax` — errors at compile time, not runtime |
| Styling       | Tailwind CSS v4                 | CSS-first config: tokens live in `src/styles/globals.css` under `@theme`, no `tailwind.config.js`                        |
| UI primitives | shadcn/ui (new-york, neutral)   | Owned-source primitives instead of a dependency; composition instead of configuration                                    |
| Routing       | TanStack Router (file-based)    | Fully type-safe routes, loaders and links; route tree generated by the Vite plugin                                       |
| Server state  | TanStack Query                  | Caching, invalidation and suspense; integrated with router loaders                                                       |
| Client state  | Jotai                           | Atomic state without boilerplate; atoms co-located with features                                                         |
| Forms         | react-hook-form + zod           | Uncontrolled performance + a single schema for validation and types                                                      |
| Unit tests    | Vitest + React Testing Library  | Shares the Vite pipeline and aliases; jsdom only where needed                                                            |
| E2e tests     | Playwright                      | Real-browser coverage of user flows; the primary tool for bug investigation                                              |

## Data flow

```
route loader ──► queryClient.ensureQueryData(xQueryOptions())
                                  │  (cache warm by render time)
component    ──► useSuspenseQuery(xQueryOptions())
mutation     ──► useMutation ──► invalidateQueries(xQueryOptions().queryKey)
```

- `queryOptions()` factories are the
  single source of truth for query keys and fetchers. Loaders and components
  consume the same factory, so keys can never drift apart.
- The router receives `{ queryClient }` as context (`app/router.ts`,
  registered in `routes/__root.tsx`), which is how loaders reach the cache.
- Route-level boundaries: `defaultErrorComponent`, `defaultNotFoundComponent`
  and `defaultPendingComponent` are configured once in `app/router.ts`
  (components in `src/app/`). Individual routes can override them via
  `errorComponent` / `pendingComponent` when they need to.
- The example feature's `api.ts` is an in-memory fake with artificial
  latency. Real projects replace the function bodies with HTTP calls and keep
  the signatures; nothing above the api layer changes.

## State management

Three kinds of state, three tools — never mix them:

1. **Server state** (anything fetched/mutated): TanStack Query. Never copy
   query data into atoms or `useState`.
2. **Client state** (UI state that outlives a component): Jotai atoms.
   Feature-scoped atoms live in `features/<name>/atoms.ts`; only genuinely
   global atoms live in `src/store/` (none currently: OnForm's property
   data is static and validated at module load in
   `features/properties/data.ts`, so the site needs no client state).
3. **Form state**: react-hook-form, validated by the feature's zod schema.
   Never mirror form values into atoms.

Ephemeral component state (an open/closed flag used by one component) is
plain `useState`.

## Environment variables

`src/config/env.ts` parses `import.meta.env` with zod once at module load
(imported first in `main.tsx`). Missing or malformed variables throw at boot
— loudly and immediately, not as `undefined` at some later point. All access
goes through the exported `env` object; `import.meta.env` is never read
elsewhere.

## Boot sequence

`main.tsx` → validate env → load global CSS → mount `<Providers>`
(QueryClientProvider + Jotai Provider, `app/Providers.tsx`) →
`<RouterProvider>` with the generated route tree.

## Deployment

The app deploys to Cloudflare Workers as static assets, configured in
`wrangler.jsonc`. There is no Worker script — Cloudflare serves `dist/`
directly (free tier, no request limits for assets) with
`not_found_handling: "single-page-application"` so deep links into TanStack
Router routes fall back to `index.html`.

- `pnpm run deploy` builds and publishes. First time on a machine:
  `pnpm exec wrangler login`.
- `VITE_*` env vars are baked in at build time (Vite), so production values
  must be present in the environment when `pnpm run deploy` runs — there is
  no runtime configuration on the Cloudflare side.
- Connecting the repo to Cloudflare Workers Builds instead works with no
  extra config: build command `pnpm build`, deploy command
  `pnpm exec wrangler deploy`, and `VITE_*` vars set in the build
  environment. Their image installs with pnpm 10.11.1, which is why
  `pnpm-workspace.yaml` is written for both pnpm 10 and 11 — see
  `docs/GOTCHAS.md`.
- The worker `name` in `wrangler.jsonc` becomes the
  `<name>.<account>.workers.dev` subdomain; custom domains are attached in
  the Cloudflare dashboard or via `routes` in `wrangler.jsonc`.
